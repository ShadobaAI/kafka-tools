# Генерация XSD

[← Инструменты AsyncAPI](../README.md)

> Команды выполняются из корня репозитория `tools`.


Генератор создаёт проверенную XSD из `components.schemas` в YAML для произвольного XDTO-формата Адаптера Kafka. Каналы и остальные разделы AsyncAPI необязательны. [Требования к YAML](https://github.com/ShadobaAI/kafka-adapter/blob/main/docs/project/yaml-requirements-for-xdto.md) и [описание генерации](https://github.com/ShadobaAI/kafka-adapter/blob/main/docs/project/xsd-generation.md) определяют поддерживаемый профиль.

### Окружение

Python 3.10 или новее. Зависимости зафиксированы в `xdto/generator/requirements.txt`; проверенное окружение — Python 3.12, PyYAML 6.0.3 и lxml 6.1.1.

```powershell
python -m venv .\xdto\.venv
.\xdto\.venv\Scripts\python.exe -m pip install -r .\xdto\generator\requirements.txt
```

### Использование

Объявления типов в XSD упорядочены так: `UUID`, общие простые типы без точки в имени, простые типы отдельных полей с точкой в имени, сложные типы. Внутри каждой группы используется сортировка по имени. Поля в `xs:sequence` сохраняют порядок `properties` исходной схемы.

```powershell
.\xdto\.venv\Scripts\python.exe .\xdto\generator\asyncapi2xsd.py <input.yaml> <output.xsd> -n <namespace> [--prefix <prefix>] [--suffix <suffix>]
```

| Аргумент | Обязательность | Назначение |
| --- | --- | --- |
| `input` | Обязателен. | YAML с непустым `components.schemas`. |
| `output` | Обязателен. | Путь результирующей XSD. |
| `-n`, `--namespace` | Обязателен. | Собственный абсолютный URI пространства имён пакета. |
| `--prefix` | Необязателен. | Начальная часть адреса топика для удаления при именовании типа. |
| `--suffix` | Необязателен. | Конечная часть адреса топика для удаления при именовании типа. |

Пример поддерживаемой модели: [supported-example.yaml](supported-example.yaml).

```powershell
.\xdto\.venv\Scripts\python.exe .\xdto\generator\asyncapi2xsd.py .\xdto\generator\supported-example.yaml .\out.xsd -n http://example.com/xdto
```

Адрес `crm.order.changed` с `--prefix crm.` и `--suffix .changed` даёт тип `Order`. При отсутствии разрешаемой связи с каналом имя берётся из ключа схемы. Все сообщения канала учитываются, неоднозначность и коллизии имён вызывают ошибку. Алиас переиспользует имя целевого типа.

### Поддерживаемая модель

| YAML | Результат |
| --- | --- |
| `string` | Именованный тип на основе `xs:string`. |
| `string`, `format: uuid` | Общий тип `UUID` с длиной 36 и шаблоном идентификатора. |
| `string`, `format: date`, `date-time`, `time` | Тип на основе `xs:date`, `xs:dateTime`, `xs:time`. |
| `integer`, без формата / `int32` / `int64` | Тип на основе `xs:integer` / `xs:int` / `xs:long`. |
| `number`, без формата / `float` / `double` | Тип на основе `xs:decimal` / `xs:float` / `xs:double`. |
| `boolean` | Тип на основе `xs:boolean`. |
| `object` | Именованный `complexType` с элементными свойствами и одной `sequence`. |
| Локальный `$ref` или алиас | Переиспользование целевого типа без изменения его вида. |
| `enum` | Ограниченный простой тип с кодами перечисления. |
| Табличный контейнер | Один объект с одним повторяющимся свойством объектных строк; дополнительная обёртка не создаётся. |

### Обязательность и пустые значения

Для массивов nullable вычисляется из отсутствия поля в `required` непосредственного родителя. Если `minItems` отсутствует, используется `0`; это относится к простым спискам, массивам объектов и массивам по локальной ссылке `$ref`.

| Поле включено в `required` | `minItems` | Пустой источник |
| --- | --- | --- |
| Нет | 0 | Поле со значением `null`. |
| Нет | >0 | Nullable отключается с предупреждением; недостаточное количество элементов является ошибкой. |
| Да | 0 | Поле со значением `[]`. |
| Да | >0 | Недостаточное количество элементов является ошибкой. |

Заполненный массив проверяется по `minItems`, `maxItems` и ограничениям каждого элемента. Nullable коллекции не разрешает null её элементов. При положительном минимуме XSD не содержит nillable=true для поля массива. Предупреждение содержит категорию `[array-nullable]`, путь YAML и минимальное количество элементов.

Профиль описывает полное состояние объекта: пустые поля массива не должны пропускаться. Скрипт генерирует XSD и проверяет default/examples, но не создаёт JSON и не заполняет отсутствующие поля. Нормализация пустого источника в null или [] и обязательный выпуск поля являются требованиями к сериализации адаптера, а не автоматически реализованным поведением XSD.

В XML простой список остаётся повторяющимся элементом: minOccurs соответствует minItems, maxOccurs — maxItems либо unbounded. При minItems=0 XML допускает отсутствие элементов; nillable относится к отдельному элементу и не обеспечивает null всего списка. Для массива объектов среди нескольких реквизитов контейнер имеет minOccurs=1; количество его row определяется minItems/maxItems. Значения атрибутов, совпадающие со стандартными значениями XSD, не записываются.

Для остальных типов прежние правила сохраняются: поле вне required допускает null независимо от минимальной границы; обязательное поле с нулевой границей может быть пропущено. Отсутствующий minLength или minimum используется как 1 для расчёта присутствия, без добавления отсутствующих фасетов типа. Это правило не распространяется на minItems.


Полное отображение, включая границы проверки повторяющихся XML-элементов, приведено в [требованиях к YAML](https://github.com/ShadobaAI/kafka-adapter/blob/main/docs/project/yaml-requirements-for-xdto.md#объекты-и-обязательность). Скрипт не сериализует рабочие сообщения: пропуск пустого поля и преобразование в null выполняются в 1С.

Inline вложенный объект получает имя типа `{Родитель}.{Поле}`. Локальная ссылка `$ref` использует имя исходного типа; дополнительные типы с автоматически добавленным обозначением `ОбщиеСвойства` не создаются. Явно заданные имена схем сохраняются.

Поддерживаются строковые границы длины и переносимый regex-профиль, числовые границы и точно представимый `multipleOf`: `10^-N` для decimal, `1` для integer. Числовые значения загружаются с сохранением десятичной точности. Возможности чисел дополнительно ограничены реализацией XMLSchema в libxml; непредставимый результат вызывает ошибку.

Regex-профиль: ASCII-литералы, положительные ASCII-классы и диапазоны, `\d`, экранированные специальные символы и обычные повторения. Поиск подстроки преобразуется в соответствующий XSD-шаблон. Wildcard `.`, группы, альтернативы, lookaround, backreference и ленивые повторения отклоняются.

`xs:documentation` содержит `title`; если он отсутствует или пуст после удаления пробелов, используется `description`. Пробелы в начале и конце удаляются, переносы строк и последовательности пробелов сворачиваются в один пробел. `default` и `examples` проверяются как значения схемы, но не записываются как default/fixed XSD. Аннотации `deprecated` и `x-*` не становятся данными сообщения; `x-enumNames` и `x-topics` необязательны.

## Массивы, группы и аннотации формата

Корневой массив и общая схема массива по $ref создают объектный тип коллекции с повторяющимся полем `row`. Исходное значение в YAML default/examples остаётся списком; при проверке оно переводится в XML коллекции. Скалярное поле, ссылающееся на такую схему, также принимает список. Границы 0 и 1 поддерживаются; неизвестные поля в примерах объектов отклоняются.

Начальный `^` и конечный `$` в pattern переводятся в ограничения начала и конца строки, сохраняя семантику поиска при отсутствии якорей. Конечный `$` требует конца входной строки, без режима multiline; завершающий перевод строки не игнорируется. Семантика якорей соответствует [ECMAScript CompileAssertion](https://tc39.es/ecma262/2024/multipage/text-processing.html#sec-compileassertion). Остальные ограничения переносимого regex-профиля сохраняются.

`format: email` поддерживается как [аннотация формата JSON Schema](https://json-schema.org/draft/2020-12/json-schema-validation#name-format-annotation-vocabular) строки и сохраняется в xs:documentation. Он не превращается в приближённый regex или неизвестный тип. minLength/maxLength/pattern и enum строки проверяются; полная проверка адреса электронной почты форматом email в XSD не выполняется. Неизвестные форматы продолжают вызывать ошибку.

### Запись значений по умолчанию XSD

Атрибут не записывается, если его вычисленное значение совпадает со стандартным значением XSD: minOccurs=1, maxOccurs=1, nillable=false, attributeFormDefault=unqualified. Отличающиеся значения сохраняются явно, например minOccurs=0, maxOccurs=unbounded, nillable=true и elementFormDefault=qualified. Это сокращение записи не меняет модель; сначала вычисляются свойства с приоритетами исходного YAML, затем сравниваются со значениями по умолчанию целевого XSD.

### Явно неподдерживаемые формы

- Вложенные массивы, включая items со ссылкой на другую схему массива.
- Произвольные словари additionalProperties=true или additionalProperties со схемой.
- `null`, `nullable`, списки типов, `allOf`, `oneOf`, `anyOf`, внешние ссылки и структурные ограничения рядом с `$ref`.
- `additionalProperties=true`, `additionalProperties` со схемой, `patternProperties`, условные схемы и неизвестные проверочные ключи.
- Специальное поле `AdditionalInfo`, boolean enum и enum/custom facets для UUID.

Объектная модель переносит объявленные `properties`. Отсутствие `additionalProperties` не является явным запретом дополнительных полей исходной JSON Schema; полная эквивалентность произвольной JSON Schema и XSD не заявляется.

Примеры `asyncapi_example.yaml`, `kfk-test.yaml` и `kfk-unit.yaml` демонстрируют поддерживаемые формы обмена. Они находятся в [examples](../examples/README.md) и поддерживаются текущим генератором. Их XSD не редактируются вручную.

### Ошибки и результат

Успех: код завершения `0`, проверенная XSD в выходном файле. Ошибка входа или файловой системы: код `2`, категория, путь определения и причина в stderr. Невалидная или частичная схема не публикуется. Выходной файл заменяется атомарно после проверки; при ошибке прежний файл сохраняется. Входной и выходной пути должны различаться.

Вход ограничен 10 MiB, 100 000 узлами и глубиной 128. Раскрытие ссылок ограничено 100 вложенными определениями; regex — 4096 символами и числовыми границами повторения до 1000; числовая запись — 1000 цифрами и модулем десятичного показателя до 1000. Дубли ключей, YAML merge и рекурсивные YAML-структуры отклоняются.

### Внутренний интерфейс

`asyncapi2xsd.generate_xsd(document, namespace, prefix=..., suffix=...)` возвращает проверенные UTF-8 байты без записи файла. Документ содержит JSON-совместимые значения; дробные числа представлены `decimal.Decimal`. `convert_file(...)` выполняет загрузку и атомарную запись. `SchemaError` содержит категорию и путь входного определения.

Вся реализация находится в одном файле `asyncapi2xsd.py`. Внутри него отдельно описаны типизированная модель, загрузка YAML, значения и фасеты, компиляция схем, выпуск XSD и CLI. CLI не содержит правил преобразования.

### Проверки генератора

```powershell
.\xdto\.venv\Scripts\python.exe -m unittest discover -s .\xdto\generator -p test_generator.py -v
.\xdto\.venv\Scripts\python.exe -m compileall -q .\xdto\generator\asyncapi2xsd.py .\xdto\generator\test_generator.py
```

Тесты отдельно проверяют JSON/XDTO-примеры, положительные и отрицательные XML-экземпляры, CLI и сохранение результата при ошибке. Проверка XML не заменяет интеграционную проверку XDTO → JSON на платформе 1С.
