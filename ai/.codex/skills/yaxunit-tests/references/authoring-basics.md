# YAxUnit Authoring Basics

Read this once when creating a test common module or materially rewriting its data setup or database assertions. These are stable defaults; use the installed YAxUnit core only for exact unknown signatures, capabilities, or incompatible runtime behavior.

- Keep `ИсполняемыеСценарии()` declarative: register a named set through `ЮТТесты.ДобавитьТестовыйНабор(...)`, then its tests/parameters through the installed `ДобавитьТест(...)`/parameter API. Use `ВТранзакции()` for server tests only when its real scope fits the side effects.
- Create common-module top-level regions according to the std455 baseline. Nest functional grouping inside the applicable standard region; do not replace it with arbitrary top-level regions.
- Name the test common module as `кфк_т_` plus the tested object-type prefix, checked object name, and applicable module suffix. For example, use `кфк_т_РС_<ИмяРегистра>_НЗ` for an information-register record-set module; a generic name such as `кфк_т_РегистрыСведений` does not identify the tested object/module.
- Assert database/register presence, absence, count, fields, or row sets through `ЮТест.ОжидаетЧтоТаблицаБазы(...)` and installed specialized predicates such as `ЧтоТаблица`/`СодержитЗаписи` by default. Use generic `ОжидаетЧто(...)` for ordinary values; a query remains valid when it is itself the tested API input. Confirm an unfamiliar chain/signature against the installed core.
- Use `ЮТест.Данные()` as the public data entry point. Prefer a shared semantic project fixture when it already represents the needed domain data; otherwise choose the narrowest suitable public operation for local scenario data, and use low-level platform creation only as a justified fallback.
- Use `СоздатьЭлемент(...)`, `СоздатьДокумент(...)`, or `СоздатьГруппу(...)` for a minimal object/reference; `КонструкторОбъекта(...)` for controlled attributes or write/post behavior; `КонструкторДвижений(...)` for supported movements/register records; and `КонструкторОбъектаXDTO(...)` for XDTO data. Set behavior-material values explicitly, generate incidental values through the suitable `Фикция*` operation or public random-value generator, and finish the builder with the terminal matching persistence, posting, or structure-only semantics. Reinitialize a builder before creating logically different data when its terminal retains configured values.
- Before filling attributes or table parts, derive their semantic roles from the tested behavior and domain contract. Keep related header values, references, rows, cardinality/order, and dependent totals coherent; in a negative test violate only the intended invariant. Set material values deterministically and generate only truly incidental values; generated data must not make behavior nondeterministic or merely type-correct but semantically invalid.
- Apply the general `$1c-code-change` method-extraction gate. In tests, keep a readable single-use fragment, tested action, and decisive expectations inline unless a well-named shared test contract materially improves comprehension or reuse.
